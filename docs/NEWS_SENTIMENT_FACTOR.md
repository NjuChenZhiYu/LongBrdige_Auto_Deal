
# 设计文档：新闻捕捉情绪指数因子 (News Sentiment Factor)

**分支**: `feature/news_capture`
**作者**: kimi-2.5-小龙虾
**日期**: 2026-03-30

## 1. 目标

构建一个能够实时捕捉市场宏观情绪的因子（Factor），通过分析与特定证券相关的新闻流，量化市场情绪，并将其应用于交易决策和市场研究。

最终目标是在自动生成的 Markdown 研报中增加 **【宏观情绪追踪】** 模块，直观地对比新闻情绪与股价走势，以发现潜在的交易机会或风险（如情绪与价格的背离）。

## 2. 数据源 (Data Source)

需要一个提供实时、全面新闻的 API。

| API 选项 | 优点 | 缺点 | 接入优先级 |
| :--- | :--- | :--- | :--- |
| **财联社 API** | - 内容质量高<br>- 实时性强（电报）<br>- A 股和港股覆盖好 | - 可能需要付费<br>- 接口文档和权限获取流程待调研 | **高** |
| **第三方聚合 API (如：Tushare, Baostock)** | - 可能已整合多家新闻源<br>- 接口相对标准，接入成本低 | - 实时性可能稍差<br>- 新闻覆盖面和质量不确定 | **中** |
| **国际新闻源 (如：Bloomberg, Reuters API)** | - 全球市场覆盖<br>- 权威性高 | - 成本高昂<br>- 主要为英文，需要额外处理 | **低** |

**初步决定**: 优先调研并尝试接入 **财联社** 的实时新闻流 API。作为备用方案，研究 Tushare Pro 的新闻接口。

## 3. 技术方案

系统将由数据捕获、情绪分析、因子计算和数据存储四个核心模块组成。

### 3.1. 数据捕获模块 (Data Ingestion)

- **实现方式**: 创建一个独立的后台服务 `NewsCaptureService`。
- **功能**:
    - 通过 WebSocket 或高频轮询 (Polling) 的方式连接新闻源 API。
    - 实时接收新闻数据（标题、正文、发布时间、相关代码等）。
    - 将原始新闻数据推送至消息队列（如 Kafka 或 Redis Stream）进行解耦，供下游处理。
- **技术选型**: Python + `websockets` / `asyncio` / `requests` + `Redis`。

### 3.2. 情绪分析模块 (Sentiment Analysis)

- **实现方式**: 创建一个消费者服务 `SentimentAnalysisService`，监听消息队列。
- **功能**:
    - 从消息队列获取新闻。
    - 调用大语言模型（LLM，如 Kimi / GPT / Ernie）的 API 对新闻标题和核心内容进行情感分析。
    - **评分标准**: 输出一个 `-1.0` (极度负面) 到 `+1.0` (极度正面) 的浮点数分值。
    - **Prompt 设计**: 设计专门的 Prompt，引导模型关注新闻对股价可能产生的影响，而不仅仅是文本的表面情绪。
        ```
        你是一个专业的金融分析师。请分析以下新闻标题和内容，判断其对相关股票（代码：{stock_code}）的潜在影响是利好、利空还是中性，并给出一个从 -1.0 (极度利空) 到 +1.0 (极度利好) 的精确评分。

        新闻标题：{title}
        新闻内容：{content}

        请仅返回一个 JSON 对象，格式如下：
        {
          "score": <your_score>,
          "reason": "<brief_reason>"
        }
        ```
- **技术选型**: Python + `moonshot` / `openai` SDK。

### 3.3. 因子计算模块 (Factor Calculation)

- **实现方式**: `FactorCalculationService`，可以定时任务或流式处理。
- **功能**:
    - 从数据库中获取最近一段时间内（如 24 小时）的所有新闻情绪评分。
    - **聚合算法**:
        - **滚动平均情绪 (Moving Average Sentiment)**: 计算过去 N 小时内所有新闻分的加权平均值（可根据新闻重要性或时效性加权）。
        - **情绪突变检测 (Sentiment Spike Detection)**: 监测情绪分在短时间内的剧烈变化。
    - 将计算出的情绪因子值（一个时间序列）存入时序数据库或关系型数据库。

### 3.4. 数据存储模块 (Data Storage)

- **数据库选型**:
    - **原始新闻和评分**: 使用 `PostgreSQL` 或 `MongoDB` 存储结构化的新闻数据和 LLM 分析结果。
    - **情绪因子时间序列**: 考虑使用 `InfluxDB` (时序数据库) 或 `PostgreSQL` 的 `TimescaleDB` 插件，便于高效查询和分析。

## 4. 研报整合 (Markdown Report Integration)

在现有的研报生成逻辑中，新增 **【宏观情绪追踪】** 模块。

- **数据提取**: 从数据库中查询指定时间段内的股价数据和对应的情绪因子序列。
- **可视化**:
    - 使用 `matplotlib` 或 `plotly` 绘制一张包含两条曲线的图表：
        1.  股价走势（K线或收盘价曲线）。
        2.  新闻情绪指数曲线。
    - 在图表上自动标注情绪指数的峰值、谷值，以及与股价发生显著背离的关键点。
- **分析文本生成**:
    - 根据图表，自动生成一段分析文本，描述近期的情绪趋势以及是否存在“价格上涨，情绪降温”或“价格下跌，情绪升温”等背离情况。
- **Markdown 嵌入**: 将生成的图表图片和分析文本插入到最终的 Markdown 研报中。

## 5. 开发步骤 (Roadmap)

1.  **第一周**:
    - [ ] 调研并确定新闻 API，完成商务或技术接入。
    - [ ] 搭建 `NewsCaptureService` 基础框架，实现从 API 获取数据并存入数据库。
2.  **第二周**:
    - [ ] 设计并测试用于情绪分析的 LLM Prompt。
    - [ ] 开发 `SentimentAnalysisService`，实现自动化新闻情感打分。
3.  **第三周**:
    - [ ] 开发 `FactorCalculationService`，实现情绪指数的计算和存储。
    - [ ] 数据库表结构设计与实现。
4.  **第四周**:
    - [ ] 在研报生成模块中增加【宏观情绪追踪】的图表和文本逻辑。
    - [ ] 联调测试，进行回测验证因子有效性。

## 6. 风险与预案

- **风险 1: API 成本过高或不稳定**
  - **预案**: 优先使用有免费额度的 API 进行开发测试；设计缓存机制，避免重复请求；准备备用数据源。
- **风险 2: LLM 情绪分析不准确**
  - **预案**: 持续优化 Prompt；引入金融领域的专用情绪词典进行辅助判断；小范围抽样人工标注，对模型进行微调 (Fine-tuning)。
- **风险 3: 因子与股价关联性不强**
  - **预案**: 调整因子计算的算法（如窗口大小、加权方式）；引入更多数据维度（如新闻来源权重、阅读量等）；明确该因子作为辅助参考，而非决策的唯一依据。
